# Topic 7 · Concepts

## 1. What is it?

Every test runs **somewhere**, on **some data**. This topic is about both.

- A **test environment** is everything a test needs around the code under test: the running services, their configuration, the databases, the network between them, and any third-party systems (real, sandboxed or stubbed).
- **Test data** is the state those tests read and change: catalogue entries, customers, orders, stock levels, accounts, files.
- **Test data management (TDM)** is the practice of creating, provisioning, isolating, refreshing, protecting and cleaning up that data, so tests are repeatable, realistic and safe.

Terms you'll meet:

- **Environment parity:** how closely an environment matches production (versions, configuration, data shape, topology).
- **Ephemeral environment:** an environment created on demand (per pull request, per test run) and destroyed afterwards.
- **Seed data:** a known baseline loaded into an environment. **Fixtures** are the data one test sets up for itself.
- **Synthetic data:** invented data generated by rules or models. It contains no real people.
- **Masking / pseudonymisation / anonymisation:** transforming real data so it can no longer identify people (fully, for anonymisation) or only with a separately kept key (pseudonymisation).

## 2. Why do we need it?

Most "the tests are unreliable" complaints are really environment and data problems:

- **Shared state makes tests flaky.** Two tests, or two teams, change the same data at the same time, and results depend on who ran first. This topic's lab shows three tests that pass alone and fail together.
- **Unrealistic data hides bugs.** Hand-made fixtures contain the cases their author thought of. Real histories contain cancellations, refunds, nulls, long names, odd time zones. The lab finds a report that's correct for the fixture and wrong for any realistic history.
- **Irreproducible data hides bugs too.** A failure found with random data you can't regenerate is a failure you can't debug.
- **Production data is a liability.** Copies of customer data in test environments are still personal data under GDPR and similar laws, usually with weaker protection. Breaches of test and staging environments are a recurring headline.
- **Environment drift breaks releases.** "It worked in staging" usually means staging wasn't like production: different versions, configuration or data volume.

The key idea is **the same artefacts, different configuration** (the "Twelve-Factor App" principle). The shop reads `PORT` and `INVENTORY_URL` from its environment. In-process tests pass them as options, `npm run start:all` uses defaults, and `compose.yaml` sets them for containers. The code is identical in every case.

### How tests get their data

There are four common strategies, often combined:

| Strategy | How | Strength | Weakness |
|---|---|---|---|
| **Shared seed** | One baseline loaded once, all tests read and change it | Simple, fast | Tests interfere; order matters; "who broke staging?" |
| **Reset per test** | Restore the baseline before each test (truncate and reseed, or a snapshot) | Isolated in sequence | Not parallel-safe in a shared environment; can be slow |
| **Transaction per test** | Run the test in a database transaction and roll it back | Fast and isolated | Only for code inside one database connection; hides commit-time behaviour |
| **Test-owned data** | Each test creates unique data it alone uses (unique IDs, its own customer, its own SKU) | Parallel-safe, even in shared environments | Needs a way to create data (factories, a test-data API); data accumulates unless cleaned up |

The lab's shared-environment tests move from the first strategy to the last.

### How synthetic data is generated

A good generator is a **model of the domain**:

1. **Valid by construction:** it uses the domain rules (the real catalogue, stock limits, `priceCart`), so every record is something the system could really contain.
2. **Realistic distributions:** most orders delivered, some cancelled, a few refunded. Lengths, nulls and edge values in realistic proportions.
3. **Seeded:** a pseudo-random generator started from a seed produces the same data every time for that seed. A failure found with seed 42 can be replayed, shrunk and debugged.
4. **Scalable:** the same generator makes 10 rows for a unit test and a million for a load test (Topic 8).

### How masking works

| Technique | Example | Keeps joins? | Reversible? |
|---|---|---|---|
| **Redaction** | Phone → `+49 000 0000000` | No | No |
| **Substitution** | Name → `Customer 7`, or a fake but realistic name | No (unless consistent) | No |
| **Unkeyed hashing** | `sha256(email)` | Yes | **Yes, by anyone with a list of emails** (dictionary attack) |
| **Keyed pseudonymisation** | `HMAC(key, email)` | Yes | Only with the key |
| **Generalisation** | Birth date → year; postcode → first two digits | Partly | No |
| **Perturbation / noise** | Amounts ± random noise | Statistical only | No |
| **Free-text scrubbing** | Detect and replace emails, phones, names in notes | — | No |

Masking has to handle **direct identifiers** (name, email, phone) and **quasi-identifiers**: fields that identify people in combination. Latanya Sweeney showed that ZIP code, birth date and sex together identify most Americans uniquely. And it has to keep **referential integrity**: the same customer must get the same pseudonym in every table, or the masked data is useless for testing.

## 4. Main components and concepts

### 4.1 Kinds of environment

| Environment | Purpose | Typical lifetime |
|---|---|---|
| **In-process** | Unit, component and API tests with services started inside the test (Topics 3–4) | Milliseconds |
| **Local** | A developer's machine: `npm run start:all`, or Compose | Hours |
| **Ephemeral / preview** | A full environment per pull request, destroyed on merge | Hours to days |
| **Shared integration / staging** | Long-lived, production-like, shared by teams | Months to years |
| **Production** | The real thing; also a test environment for canaries and synthetic checks (Topic 10) | Forever |

The trend is away from long-lived shared environments and towards ephemeral ones plus contracts (Topic 4). Shared environments are expensive, drift away from production, and are the commonest source of "someone else broke my test".

### 4.2 Environment parity: the three gaps

From the Twelve-Factor App: keep development, test and production as similar as possible across three gaps:

- **Time gap:** how long before code written reaches an environment. Continuous deployment shrinks it.
- **Personnel gap:** who deploys and operates it. Developers deploying their own code shrinks it.
- **Tools gap:** different databases, OS or versions. Containers and pinned versions shrink it (the shop's `Dockerfile` uses the same Node major version as `.nvmrc`).

### 4.3 Configuration

- Read configuration from the **environment**, not from code branches like `if (env === 'staging')`.
- Make **dangerous switches opt-in**. The inventory service's test-data API is off unless `INVENTORY_TEST_DATA=on`; production never sets it.
- **Fail loudly** on missing required configuration rather than silently falling back to a default that points somewhere surprising.
- Keep **secrets out of the repository**. The lab's `MASK_KEY` comes from the environment, never from a file in Git.

### 4.4 Test data patterns in code

- **Builders / factories:** `anOrder().withBook(5).cancelled().build()` creates valid objects with sensible defaults, so each test states only what matters to it.
- **Object mothers:** named, ready-made examples (`TestCustomers.withExpiredCard()`).
- **Unique identifiers:** generated per test (`ownBook()` in the lab), so parallel tests never collide.
- **Cleanup:** delete what you created, rely on expiring data (the inventory's 15-minute holds), or throw away the whole ephemeral environment.

### 4.5 Data for different test levels

| Level | Data | Source |
|---|---|---|
| Unit | Tiny, explicit, in the test | Inline literals, builders |
| Component / API | Small, controlled | Factories; in-memory stores; a reset per test |
| Integration | Realistic shapes | Generated, seeded; test-owned records |
| E2E | Whole journeys | API setup per test (Topic 5); seeded catalogue |
| Performance | Production-like volume and distribution | Generators at scale; masked production statistics |
| Exploratory / UAT | Realistic and varied | Masked production subsets, or rich synthetic data |

### 4.6 Privacy rules that apply to test data

- **GDPR** (and similar laws such as the UK GDPR and California's CCPA/CPRA): personal data used for testing is still personal data. It needs a lawful basis, minimisation and protection. Pseudonymised data is *still* personal data under GDPR; only truly anonymised data falls outside it.
- **PCI DSS:** real card numbers must never be in test environments; use the payment provider's test tokens (the shop's `tok_visa`).
- **Data minimisation:** copy only the fields and rows a test needs. Most tests need none of the real data.

## 6. How it connects with other practices

| Practice | Connection |
|---|---|
| **Test design (Topic 2)** | Generators make property-based testing possible at the data level; partitions tell you which data variety you need |
| **Unit and component (Topic 3)** | Builders and in-memory fakes are test data tools |
| **Contracts (Topic 4)** | Provider states are named test data setups; contracts reduce the need for shared integration environments |

## 7. Real-world examples

**1. Three tests, one book (this repo).** Three tests each assume book 5 starts with 3 copies. Run one at a time against a shared inventory service, they pass. Run in parallel, they fail every time: each one changes the stock the others are reading. Resetting the data doesn't fix it (a reset in the middle of someone else's test is just another collision). Giving each test its own book through a test-data API does, and the same tests then pass 10 runs out of 10 in parallel.

**2. The report that counted refunds (this repo).** The sales report's hand-made fixture has three delivered orders, and every assertion passes. A generated history with a realistic mix of states shows the report counting cancelled and refunded orders as revenue. Any finance team would spot it in the first real month. Realistic data is a test oracle's best friend.

**3. The masking script (this repo).** Names replaced, phones starred, emails hashed. And yet: names and phone numbers sit untouched in delivery notes; order emails are "masked" by keeping the person's name; and the email hashes are plain SHA-256, so anyone with a customer list can reverse them. On top of that, orders no longer join to customers, so the data is useless for testing anyway. Each mistake is common in real masking scripts.

**4. The Netflix Prize and AOL search data (2006).** Both organisations released "anonymised" datasets; researchers re-identified individuals by combining them with public information (movie ratings on IMDb; distinctive search queries). Removing names isn't anonymisation when the remaining data is distinctive.

**5. Staging breaches.** Security incidents involving test and staging environments that held copies of production data recur across industries, because those environments get weaker access control, older software and less monitoring than production. The lesson most organisations draw: don't put real personal data there in the first place.

## 8. Scaling across applications and teams

| Challenge | What works |
|---|---|
| Teams queue for one staging environment | **Ephemeral environments** per pull request (Compose, Kubernetes namespaces, preview environments), plus contracts instead of shared integration |
| Every team writes its own data setup | Shared **builders and test-data APIs** owned by the service teams, documented like any API |
| Masking scripts scattered and unreviewed | A central, reviewed **masking pipeline** with PII scanning as a gate; data catalogues that tag personal fields |
| Synthetic data that drifts from reality | Generators calibrated from **aggregate production statistics** (distributions, not records) |
| Test data piling up in long-lived environments | Expiry by design (TTL), test-run tagging, and scheduled cleanup |
| Environment cost | Spin down when idle; share read-only infrastructure; size ephemeral environments to the tests that need them |

## 9. Security and data privacy

- **Test-data APIs are dangerous in production.** `PUT /stock` would let anyone set any stock level. Keep such endpoints behind an opt-in switch that production never sets, and test that it's off there (Topic 9).
- **Don't copy production data by default.** Synthetic data first; masked subsets only when there's a real need, with an owner and an expiry.
- **Pseudonymised ≠ anonymous.** Keyed hashes can be reversed by whoever holds the key; keep the key out of test environments and the repository.
- **Free text is where PII hides:** notes, comments, addresses typed into the wrong field, log messages. Scan for it.
- **Quasi-identifiers combine.** City + postcode + order dates + amounts can single out a person in a small dataset. Generalise or perturb where it matters.
- **Logs and traces** in test environments carry whatever data the tests used. Another reason to use synthetic data.
- **Containers:** run as a non-root user (the shop's `Dockerfile` uses `USER node`), keep secrets out of images and build logs, and pin base images.

## 10. Performance, maintenance, and cost

| Concern | Guidance |
|---|---|
| **Startup time** | In-process: milliseconds. Compose: seconds to a minute (image builds are cached). Full staging deploys: minutes. Use the cheapest environment that answers the question. |
| **Data setup time** | API-created test data is slower than in-memory fixtures, but far faster than UI setup. Batch it per test file where safe. |
| **Generator cost** | Seeded generators are cheap to run and cheap to maintain *if* they reuse domain code (`priceCart`), so they don't drift from the rules. |
| **Masking cost** | A masking pipeline is code with high stakes: test it (the PII scan is a test). |
| **Environment cost** | Long-lived environments cost money around the clock; ephemeral ones cost only while used. |
| **Maintenance** | Shared seed data becomes a hidden dependency of hundreds of tests. Test-owned data keeps each test's assumptions visible. |

## 11. Common problems and failure scenarios

| Problem | Symptom | Fix |
|---|---|---|
| **Tests share mutable data** | Pass alone, fail together or in another order | Test-owned data; unique IDs |
| **Reset in a shared environment** | One test's reset wipes another's data mid-test | Isolation per test or per environment, not resets |
| **Fixtures only cover the happy path** | Production finds edge cases the tests never had | Generated, realistic distributions; property-based checks |
| **Unseeded random data** | A failure can't be reproduced | Seeded generators; log the seed |
| **Production copies in test** | Compliance and breach risk | Synthetic data; masked, minimised subsets with expiry |
| **Masking breaks joins** | Masked data is useless, so people go back to raw copies | Consistent, keyed pseudonyms |
| **Environment drift** | Passes in staging, fails in production | Infrastructure and configuration as code; same images everywhere |
| **Dangerous test switches reach production** | Data tampering, debug endpoints exposed | Opt-in configuration; a test that checks they're off in production |

## 12. Important trade-offs

- **Realism vs privacy.** Production data is the most realistic and the most dangerous. Synthetic data is safe, but only as realistic as its generator.
- **Shared vs ephemeral environments.** Shared environments are cheap to keep running and expensive in interference; ephemeral ones isolate but cost provisioning time.
- **Speed vs fidelity.** In-memory fakes are fast but differ from the real database; containers are realistic but slower to start.
- **Determinism vs coverage.** Fixed seeds make failures reproducible; new seeds explore more. Fix the seed in CI, vary it locally or nightly, and log it always.
- **Masking strength vs usefulness.** The more you redact, the less the data looks like real life. Decide per field, per test purpose.

## 13. Comparisons

### Ways to provide an environment

| Approach | Speed | Fidelity | Isolation | Notes |
|---|---|---|---|---|
| In-process services (Topics 3–4) | ⚡⚡⚡ | Medium | Full | Best for most automated tests |
| Docker Compose (this lab) | ⚡⚡ | High | Full per machine | Local and CI; not production topology |
| Testcontainers | ⚡⚡ | High | Per test suite | Real databases and brokers started from test code |
| Kubernetes namespace / preview env | ⚡ | Very high | Per pull request | Matches production platforms |
| Shared staging | 🐢 to change | High (if maintained) | None | Useful for final checks; poor default |
| Service virtualisation (WireMock, Hoverfly) | ⚡⚡⚡ | Depends on the stub | Full | For third parties you can't run; keep honest with contracts |

### Ways to get test data

| Approach | Realism | Privacy risk | Reproducible | Notes |
|---|---|---|---|---|
| Hand-written fixtures | Low | None | Yes | Precise for unit tests |
| Builders / factories | Medium | None | Yes | Readable, flexible |
| Seeded synthetic generators | Medium–high | None | Yes | Valid by construction if built on domain code |
| Faker-style libraries (Faker, Bogus, Mimesis) | Medium | None | With a seed | Realistic-looking values, no domain rules on their own |
| Masked production subsets | High | Medium | Snapshot | Needs strong masking and governance |
| Raw production copies | Highest | **High** | Snapshot | Avoid |
